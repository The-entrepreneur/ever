This is where a mobile app genuinely makes sense — but only for one specific part of the platform. The Live Inbox.

A guest sends a WhatsApp message at 11pm requesting urgent assistance. The bot triggers a handoff. The hotel manager is not at a desktop. **On-the-go Live Inbox access** — a receptionist is not at a desk all day. They are at the front desk, walking the property, attending to guests in person. When a handoff comes in, they need to be able to pick up their phone, read the guest's message, see the bot summary card, type a reply, and send it — all from the property floor.

The other screens — Analytics, Knowledge Base, Bot Settings, Leads, Billing — are perfectly fine on a web dashboard. Nobody needs to update their FAQ answers while walking down a hotel corridor. But the Live Inbox is genuinely mobile-first in its use pattern.

## The Right Approach — What to Build and When

**Phase 3 (now, during dashboard build) — Progressive Web App (PWA)**

The EVER dashboard is being built in Next.js on Vercel. Making it a PWA is configuration, not a new project. You add a web manifest, a service worker, and PWA-specific meta tags. The hotel manager installs it from their browser to their home screen like an app. It gets its own icon, opens full screen without browser chrome, and — critically — can receive push notifications via the Web Push API even when the browser is not open.

This covers 85% of the mobile app use case with zero additional development cost and no App Store involvement. The Live Inbox renders on mobile, push notifications work via Web Push, handoffs are actionable from a phone. Build this during the dashboard sprint — it is not a separate project.

**Phase 4 (when you have 10+ active hotel clients with active staff) — Native App**

The genuine limitation of a PWA on iOS is that Apple restricts Web Push notifications on iOS Safari to apps added to the home screen, and even then it is less reliable than a native push notification. On Android PWA push notifications are fully reliable. On iOS they are notionally supported from iOS 16.4 onward but in practice still have edge cases.

Once you have hotel staff who are on iPhones — which is a realistic assumption for a UK or European hotel property — and who are missing handoff alerts, that is the signal to build a native app. A React Native app reuses the component logic from your Next.js dashboard. Expo in particular lets you share a large percentage of code between web and native. The Live Inbox, notification handling, and the key action buttons (Take Over Chat, Send Message, End Chat) are the only screens that need to be native. Everything else can be a WebView pointing at the web dashboard.

**Screen 2 — Chat Window**
